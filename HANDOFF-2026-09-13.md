### 2. PNG file hashes are not a parity comparator — a T04 trap, now closed

This is the finding worth your attention.

Blender stamps the render wall-clock into the beauty PNG's `tEXt` chunks
(`Date`, `RenderTime`, `cycles.ViewLayer.total_time`, `render_time`). Two
bit-identical renders therefore hash differently. Your own evidence proves it:
the accepted v6 reference and your September 12 dark regression are both 501,813
bytes with the same IDAT payload (`101347d996e3b7ed…`, 500,441 bytes) and differ
only in those timestamps. File hashes `bfe42875da17c72f…` vs `61c93fc1f58f8067…`;
decoded pixels identical.

`mask.png` and `composite.png` never show this, because Pillow writes them and
stamps no timestamp — which is exactly why the drift is easy to miss. Only the
one artifact that comes straight out of Blender is affected.

A cross-device T04 gate keyed on the profile's `reference_sha256` would fail on
identical hardware for no reason but the clock. Nothing compares that field
today, so it was latent, not live.

`pixel_digest()` in `scripts/verify_scene.py` now hashes the decoded mode, size
and pixel bytes, and `scene-parity-profile.json` records
`reference_pixels_sha256`, `reference_mask_pixels_sha256` and
`reference_composite_pixels_sha256` beside the existing file hashes.
**Compare those across devices.** Three tests in `TestPixelDigest` cover it:
metadata drift, a one-pixel change, and an unreadable file. The file hashes stay
in the profile as a record of the exact bytes produced, not as a comparator.

Written up in `docs/rl300-parity.md`, section *PNG file hashes are not a parity
comparator*.

### 4. `owner_accepted` — question answered, schema deliberately unchanged

Mark accepted v6, yet every report says `owner_accepted: false`, because
`docs/scene_parity.schema.json` pins it to `const: false`. He was asked whether
to widen it and left the call here. **It stays `const: false`**, and the
schema now carries a `description` saying why, so the next person to notice the
mismatch does not "fix" it.

The reasoning, in full in `docs/rl300-parity.md`: the report is the verifier's
testimony about a run it performed; owner acceptance is an out-of-band human
decision it cannot observe. A verifier-authored `true` would be a claim it has
no standing to make, and a hand-edited `true` in a machine-generated file is the
exact failure mode the frozen-hash discipline exists to prevent. If T04 later
needs a machine-readable acceptance gate, add a *separate* acceptance record
keyed to the reference composite SHA-256 — do not widen this schema.
