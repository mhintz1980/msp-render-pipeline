## What is next — T04, and what it actually needs

T04 is cloud parity: prove the same prepared payload renders the same picture on
cloud hardware as it does locally. Nothing of it has started. In rough order:

1. **Transport.** Get the prepared payload to cloud hardware and render it there
   with the same pinned runtime. `verify_scene.py` already pins runtime version,
   build and archive SHA-256 into every report — that pin is what makes a
   cross-device comparison mean anything, so carry it, do not reproduce it.
2. **Compare by pixel digest, never file hash.** `scene-parity-profile.json`
   carries `reference_pixels_sha256`, `reference_mask_pixels_sha256` and
   `reference_composite_pixels_sha256` for exactly this. Blender stamps the
   render wall-clock into `beauty.png`'s `tEXt` chunks, so two bit-identical
   renders have different file hashes. A comparison keyed on `reference_sha256`
   would fail on *identical* hardware for no reason but the clock. This is
   written up at
   [PNG file hashes are not a parity comparator](docs/rl300-parity.md#png-file-hashes-are-not-a-parity-comparator).
3. **Expect the mask gate to break first.** The mask is product-plus-shadow, so
   the IoU ≥ 0.995 and coverage-delta ≤ 0.005 gates sit on a soft boundary: the
   shadow edge is illumination- and denoise-dependent and coverage is decided at
   **mask byte 8**. It is recorded as the most likely threshold to break first on
   different hardware. If it does, that is a calibration finding to bring to Mark
   with numbers — **not** a licence to widen a threshold.
4. **Do not widen `scene_parity.schema.json`.** `owner_accepted`, `g0_passed` and
   `cloud_authorized` are hardcoded false in verifier output *by design* — their
   being unforgeable is what makes the reports worth trusting. If T04 needs a
   machine-readable acceptance gate, add a **separate** acceptance record keyed to
   the reference composite SHA-256.
5. **`cloud_authorized` is a human gate.** Live cloud spending is still not
   authorised. A passing local suite does not imply it, and neither does a
   passing cloud run. Ask Mark; get it in writing; record it the way the
   acceptances above are recorded.

After that, **T05** is general compositor hardening. `docs/color-study-2026-09-11.md`
notes explicitly that the colour work done there does not assert the T05 contract
is complete, so treat T05 as unscoped until someone writes its clauses down the
way T03's were written.

## How this session went wrong, four times, and what each cost

Worth reading before you touch the geometry script — every one of these was a
gate that passed while the model was wrong.

1. **Every placement gate was radial or rotational.** Bolt circle to 3 µm, hole
   phase to 0.12° — and a replacement flange of a different thickness passed all
   of them while burying the bolts and washers inside itself. Nothing measured
   the axial stack. `seat_flange_hardware()` now does.
2. **I diagnosed it backwards first.** I read the space the misplaced hardware
   left as the design requirement and concluded the flange was too thick. Mark
   corrected me with the real stack — 1.125 + 0.125 + 0.500 in. When a
   measurement and the owner's drawing disagree, the drawing is the spec.
3. **An appearance fix lived in one job manifest out of four.** The stainless
   latch was fixed on 2026-09-12 in the white job only, so three jobs including
   the anchor rendered a plastic latch for a day. Corrections that describe the
   *model* now live in the source, not a manifest.
4. **One part number, two meshes, one of them forgotten.** `F8Z-075` is at two
   joints. v7 widened `Mesh_205` and left `Mesh_226`, so the machine wore two
   different washers for five versions. `widen_washers()` now iterates a list.

The pattern: a gate that only checks one axis, one job, or one mesh will pass
while the thing it names is wrong. When you add a check, ask what it does *not*
look at.
